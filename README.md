## エージェント機能の使い方

GitHub Copilot のエージェント機能を使うと、単なるコード補完だけでなく、**調査・修正案の提示・複数ステップの作業支援**まで対話形式で進められます。

### できること

- バグの原因調査
- 関連ファイルの探索
- 実装方針の提案
- コードの修正案作成
- テスト追加やリファクタリングの支援
- Pull Request の要約やレビュー補助

### チャットで対象を指定して依頼するときのコマンド例

Copilot Chat では、ソースコード・ターミナル出力・Git の差分や履歴など、**見てほしい対象を明示して依頼する**と精度が上がります。以下はよく使う例です。

| 指定方法 | 主な用途 | 依頼例 |
| --- | --- | --- |
| `@workspace` | ワークスペース全体を対象に、関連実装を広く調べたいとき | `@workspace この認証処理の流れを説明して` |
| `#file:README.md` | 特定ファイルを明示して確認・修正したいとき | `#file:README.md セットアップ手順として不足している説明を追加して` |
| `#file:src/auth.ts` | 実装ファイル単位でレビューや修正案を依頼したいとき | `#file:src/auth.ts この関数に日本語コメントを付けて` |
| `#selection` | いま選択しているコード範囲だけを見てほしいとき | `#selection このコードの問題点を指摘して` |
| `#terminal` | ターミナルの直近出力をもとに原因調査したいとき | `#terminal このビルドエラーを解消する手順を教えて` |
| `#terminalLastCommand` | 直前に実行したコマンド結果に絞って見てほしいとき | `#terminalLastCommand 直前に実行したコマンドの結果から問題点を整理して` |
| `#terminalSelection` | ターミナル出力の一部だけを対象に相談したいとき | `#terminalSelection このログ範囲だけを見て異常箇所を特定して` |
| `#changes` | 未コミット差分や変更内容をレビューしてほしいとき | `#changes この変更内容をレビューして` |
| `#codebase` | リポジトリ内の関連箇所を横断的に探したいとき | `#codebase この機能に関連する実装箇所を広く探して` |
| `#problems` | 検出されている問題一覧をもとに優先度を相談したいとき | `#problems 現在検出されている問題の中で優先して直すべきものを教えて` |
| `#tests` | 必要なテスト観点や追加ケースを相談したいとき | `#tests この変更で追加すべきテストケースを提案して` |
| `#githubRepo` | GitHub 上のリポジトリ文脈を前提に相談したいとき | `#githubRepo このリポジトリの構成を踏まえて改善方針を出して` |
| `#githubPullRequest` | PR を対象に要約・レビュー補助を依頼したいとき | `#githubPullRequest このPRのレビューコメント案を作って` |

#### 組み合わせて依頼する例

| 組み合わせ例 | 用途 |
| --- | --- |
| `#file:src/api.ts #terminal このエラーが起きる原因をコードとログから特定して` | コードとログを合わせて原因を絞り込む |
| `#selection #changes この修正方針で差分が妥当か確認して` | 選択範囲と差分を見比べて修正方針を確認する |
| `@workspace #terminal このリポジトリ全体を見て、このエラーの原因箇所を絞り込んで` | 全体構造とログを踏まえて原因箇所を探索する |
| `#file:README.md #changes 今回の変更内容に合わせて README も更新して` | 実装差分に追従するドキュメント更新を依頼する |
| `#terminalLastCommand #file:package.json 依存関係エラーの原因を特定して` | コマンド結果と設定ファイルを組み合わせて依存関係問題を調べる |

### エージェントのツールの種類

GitHub Copilot のエージェント機能で使われるツールは、用途に応じて大きく **組み込み**, **拡張機能**, **MCP** の3種類に分けて考えると理解しやすいです。

#### 組み込みツール

組み込みツールは、Copilot やチャット環境に最初から用意されている標準機能です。  
主に、**現在のワークスペースや編集中の情報を読み取り、調査や提案に使うための機能**です。

たとえば、次のような文脈をもとにエージェントが支援できます。

- ワークスペース全体を対象に関連実装を探す
- 特定ファイルを読んで説明や修正案を出す
- 選択中のコード範囲だけを見て改善点を挙げる
- ターミナル出力からエラー原因を調べる
- 変更差分を確認してレビューする
- リポジトリや Pull Request の文脈を踏まえて要点を整理する

README 内で紹介している `@workspace`, `#file`, `#selection`, `#terminal`, `#changes` などは、こうした組み込みツールに関連する文脈指定の例として考えるとわかりやすいです。

#### 拡張機能のツール

拡張機能のツールは、VS Code などの拡張機能によって追加される機能です。  
標準機能だけでは扱えない対象や、特定の技術領域に特化した支援を追加できます。

たとえば、次のような用途があります。

- Docker やコンテナ設定を確認する
- データベース関連の情報を扱う
- Kubernetes やクラウド設定を参照する
- テストや静的解析ツールの結果を活用する
- 独自の開発支援ツールと連携する

利用できる内容は、導入している拡張機能や利用環境によって異なります。

#### MCP

MCP は **Model Context Protocol** の略で、エージェントが外部ツールや外部サービスと連携するための仕組みです。  
エディタ内の情報だけでなく、**IDE の外にあるシステムやデータソースも活用できる**ようになります。

たとえば、MCP を通じて次のような連携が考えられます。

- 社内ドキュメントやナレッジベースを検索する
- Issue 管理ツールやチャットツールを参照する
- 独自 API や業務システムを呼び出す
- データベースや外部サービスに問い合わせる
- 独自の社内ツールをエージェントから利用する

MCP を使うことで、エージェントはコード補助だけでなく、より広い業務支援に活用しやすくなります。

### ツールセットとは

エージェントモードにおける **ツールセット** は、エージェントに利用させるツール群を用途ごとにまとめて管理する考え方です。  
毎回すべてのツールを前提にするのではなく、**この作業ではどのツールを使ってよいかを整理しておく**ことで、目的に合った依頼をしやすくなります。

たとえば、次のように使い分けるイメージです。

- **コード調査用ツールセット**  
  ワークスペース参照、コード検索、差分確認などを中心に使う
- **ドキュメント更新用ツールセット**  
  ファイル参照、README 編集、関連差分確認などを中心に使う
- **外部連携用ツールセット**  
  MCP 経由の検索、社内ツール参照、API 呼び出しなどを含める
- **レビュー補助用ツールセット**  
  PR 文脈、差分確認、テスト観点整理などを中心に使う

このようにツールセットを意識すると、エージェントに対して「何を見て、どこまでやってよいか」を伝えやすくなります。

### エージェントモードでのツールセット作成手順

ここでは、**利用可能な機能の上限が 128 個**であることを前提に、必要最小限のツールセットを作る手順を示します。  
画面名称はバージョンで多少異なる場合がありますが、進め方は同じです。

1. **作成画面を開く**  
  Copilot Chat のエージェントモードで、ツールセット管理画面を開きます。

2. **新規ツールセットを作成する**  
  まず名前を付けます。名前は用途が一目で分かるものにします。  
  例: `docs-minimal`, `code-investigation-core`, `pr-review-lite`

  設定例（JSONC）:

  ```jsonc
  {
    "readme-update-minimal": {
      "tools": [
        "#file:README.md",
        "#changes"
      ],
      "description": "README更新専用。差分確認に限定した最小構成",
      "icon": "book"
    }
  }
  ```

3. **目的を 1 つだけ決める**  
  1 つのツールセットに複数目的を混ぜないのが重要です。  
  例: README 更新専用、コード調査専用、レビュー専用

  設定例（目的を分離）:

  ```jsonc
  {
    "readme-update-minimal": {
      "tools": ["#file:README.md", "#changes"],
      "description": "README更新専用",
      "icon": "book"
    },
    "review-selection-minimal": {
      "tools": ["#selection", "#changes", "#problems"],
      "description": "選択範囲レビュー専用",
      "icon": "eye"
    }
  }
  ```

4. **必須ツールだけを追加する**  
  目的達成に直接必要なものだけを選択します。  
  README 更新なら、まずは `#file` と `#changes` のような最小構成から始めます。

  最小構成の例（必要なものだけ有効化）:

  ```jsonc
  {
    "readme-update-minimal": {
      "tools": [
        "#file:README.md",
        "#changes"
      ],
      "description": "README更新専用",
      "icon": "book"
    }
  }
  ```

  依頼文サンプル:

  ```text
  #file:README.md #changes 今回の差分に合わせてREADMEの説明を更新して
  ```

5. **迷うツールは一旦入れない**  
  後で不足したら足す方針にします。  
  最初から広く入れると 128 個上限に近づき、運用が重くなります。

6. **MCP と拡張機能ツールは分離する**  
  外部連携系は依存関係や認証が増えるため、通常作業セットと分けます。  
  例: `readme-editing-minimal` と `mcp-research`

7. **保存後に短い依頼で動作確認する**  
  実際に 1 回依頼して、不要なツールが混ざっていないか確認します。  
  例: `#file:README.md #changes 差分に合わせて説明を更新して`

8. **週次または月次で棚卸しする**  
  使っていないツールは外し、必要になったものだけ追加します。  
  この運用で、128 個上限を継続的に守りやすくなります。

### 128 個上限を守るための設計ポイント

- **1 ツールセット 1 目的を徹底する**
- **共通作業は軽量な基本セットを作って使い回す**
- **外部連携（MCP）は必要時のみ有効化する**
- **定期的に未使用ツールを棚卸しして削除する**
- **不足が出たら追加、不要になったら削除の運用にする**

### MCP ツールの設定方法と使い方
#### VS Code で公開 MCP ツールを追加する場合

VS Code で GitHub Copilot のエージェントモードから **公開 MCP ツール** を使いたい場合は、  
**MCP サーバーの設定を VS Code 側に追加**します。

流れとしては、次のように考えるとわかりやすいです。

1. **追加したい公開 MCP サーバーを決める**  
   まず、利用したい公開ツールの配布ページや説明を確認します。  
   そこに、VS Code や MCP 用の設定例、必要なコマンド、環境変数、API キーなどが書かれていることがあります。

2. **必要な情報を確認する**  
   MCP サーバーごとに、必要な項目は異なります。たとえば次のような情報を確認します。
   - サーバー名
   - 実行コマンド
   - 引数
   - 接続先 URL
   - API キーやトークン
   - 環境変数
   - インストール方法

3. **VS Code の MCP 設定に追加する**  
   利用している環境の手順に従って、MCP サーバー定義を設定します。  
   一般的には、設定ファイルに `mcpServers` のような形で追加します。

4. **必要なら認証情報を設定する**  
   公開ツールによっては API キーが必要です。  
   その場合は、説明に従って環境変数などを設定します。

5. **VS Code で Copilot Chat / エージェントから使えるか確認する**  
   設定後、Copilot Chat でエージェントモードを使い、対象ツールを利用する依頼を行います。  
   たとえば「この公開 MCP ツールを使って調べて」と依頼すると、文脈に応じて利用されることがあります。

#### 設定イメージ

```json
{
  "mcpServers": {
    "playwright-mcp": {
      "command": "npx",
      "args": ["-y", "@playwright/mcp@latest"],
      "env": {
        "PLAYWRIGHT_BROWSER": "chromium",
        "PLAYWRIGHT_HEADLESS": "true"
      }
    }
  }
}
```

※ この JSON は Playwright MCP 向けの構成例です。  
配布元の仕様変更でパッケージ名や環境変数名が変わる場合があるため、利用時は公式 README も合わせて確認してください。

#### VS Code で追加するときの見方

公開 MCP ツールの説明を読むときは、次のような項目に注目すると理解しやすいです。

- `command`  
  MCP サーバーを起動するコマンドです。`node`、`npx`、`python` などが使われることがあります。

- `args`  
  コマンド実行時の引数です。パッケージ名や起動オプションが入ることがあります。

- `env`  
  API キーや接続設定など、環境変数を渡すための項目です。

- サーバー名  
  複数の MCP ツールを区別するための識別名です。

#### 追加後の依頼例

設定後は、たとえば次のように依頼できます。

- 「MCP のドキュメント検索ツールを使って、この技術の公式仕様を調べて」
- 「追加した公開 MCP ツールを使って関連情報を要約して」
- 「この API について、MCP 経由で取得できる情報を確認して」
- 「タスク管理ツールの MCP を使って、未対応タスクを整理して」

#### エージェントモードで MCP（手動）を設定する場合

エージェントモードで **MCP を手動設定**したい場合は、公開サーバーの説明を見ながら、必要な項目を自分で構成して VS Code 側に登録します。  
自動で追加される仕組みではなく、**利用する MCP サーバーの起動方法や認証情報を確認して、自分で設定を書く**イメージです。

基本的な進め方は次の通りです。

1. **利用したい MCP サーバーの配布ページや README を確認する**  
   手動設定では、まずその MCP サーバーがどのように起動されるかを把握します。  
   たとえば `npx` で起動するのか、`docker` を使うのか、ローカルの `python` スクリプトとして動かすのかを確認します。

2. **必要な設定値を整理する**  
   README や配布ページから、以下のような情報を抜き出します。
   - サーバー名
   - 実行コマンド
   - 引数
   - 必要な環境変数
   - API キーやアクセストークン
   - 接続先 URL
   - 事前インストールが必要なランタイムやパッケージ

3. **VS Code の MCP 設定に手動で追記する**  
   `mcpServers` に対象サーバーを追加します。  
   サーバーごとに `command`、`args`、`env` などを定義し、Copilot から呼び出せる状態にします。

4. **機密情報は安全に扱う**  
   API キーやトークンを使う場合は、設定例をそのまま README に貼るのではなく、環境変数や安全なシークレット管理方法を使うのが望ましいです。

5. **エージェントモードから利用確認を行う**  
   設定後に Copilot Chat のエージェントモードで、対象 MCP を使う前提の依頼をして、意図どおり呼び出されるか確認します。

#### 手動設定のイメージ

```json
{
  "mcpServers": {
    "playwright-mcp-local": {
      "command": "node",
      "args": ["./tools/playwright-mcp-server.mjs"],
      "env": {
        "PLAYWRIGHT_BROWSER": "chromium",
        "PLAYWRIGHT_HEADLESS": "false"
      }
    }
  }
}
```

この例では、ローカルの Node スクリプトで Playwright MCP サーバーを起動する想定です。

実装ファイルのイメージ:

```javascript
import { spawn } from "node:child_process";

// ローカルラッパー経由で Playwright MCP を起動する最小例
const child = spawn("npx", ["-y", "@playwright/mcp@latest"], {
  stdio: "inherit",
  env: {
    ...process.env,
    PLAYWRIGHT_BROWSER: process.env.PLAYWRIGHT_BROWSER ?? "chromium",
    PLAYWRIGHT_HEADLESS: process.env.PLAYWRIGHT_HEADLESS ?? "false"
  }
});

child.on("exit", (code) => process.exit(code ?? 0));
```

初回のみ、ブラウザ実行環境が必要な場合は次を実行します。

```bash
npx playwright install chromium
```

#### 手動設定で確認したいポイント

- `command` がローカル環境で実行可能か
- `args` が README の説明どおりになっているか
- 必須の環境変数が不足していないか
- API キーやトークンを安全に渡せているか
- VS Code / Copilot Chat 側で対象 MCP が認識されるか

#### 手動設定時の注意点

- MCP サーバーごとに起動方法が異なるため、**README の設定例をそのまま流用できるとは限りません**
- `python`、`node`、`docker` など、前提となる実行環境が手元に必要な場合があります
- 社内向け MCP の場合は、VPN、社内ネットワーク、追加認証が必要なことがあります
- 認証情報を設定ファイルへ直書きするより、環境変数で管理するほうが安全です
- 動かない場合は、まず MCP サーバー単体で起動できるかを確認すると切り分けしやすいです

#### MCP設定時の注意点

- VS Code 側が **MCP サーバー設定に対応していること** が前提です
- 利用方法は、GitHub Copilot Chat のバージョンや VS Code の機能更新によって変わることがあります
- 公開 MCP サーバーによっては、ローカルで追加パッケージのインストールが必要です
- API キーを使う場合は、README に直接ベタ書きせず、安全な方法で管理するのが望ましいです
- 外部ツールは便利ですが、**取得結果の正確性や安全性は必ず確認**します

### 使い分けの目安

- **コードや設定ファイル、ログをもとに調査したい場合**  
  → 組み込みツール
- **特定技術向けの追加支援を使いたい場合**  
  → 拡張機能のツール
- **外部サービスや社内システムと連携したい場合**  
  → MCP

### 補足

利用できるツールの種類や名称、指定方法は、GitHub 上の Copilot Chat、VS Code 拡張、導入済み拡張機能、MCP サーバー設定などによって異なる場合があります。

### うまく使うコツ

- 依頼はできるだけ具体的にする
- 対象のリポジトリ・ブランチ・ファイルを明示する
- 「何を変えたくないか」も伝える
- 一度に大きく頼みすぎず、段階的に依頼する
- 出力結果はそのまま使わず、必ず確認する

### 依頼テンプレート

```markdown
目的: 何をしたいか
対象: リポジトリ / ファイル / PR / Issue
現状: 困っていること・エラー内容
期待結果: どうなってほしいか
制約: 変更したくない部分、使用技術、コーディング規約
```

### 注意点

- 自動生成されたコードや説明は必ずレビューする
- 権限が必要な操作は、環境や設定によって実行できない場合がある
- 曖昧な依頼だと、意図と異なる提案になることがある

### まとめ

エージェント機能は、**「質問して終わり」ではなく、開発作業を一緒に進めるための支援機能**です。  
具体的な依頼と十分な文脈を渡すことで、より実用的な提案を得られます。
